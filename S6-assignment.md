16. The Assignment

Build a small but complete Training Data Execution System for V5.

The system must implement the full path:

documents
-> tokenized shards
-> manifests
-> mixture schedule
-> packing
-> batches
-> training
-> consumption ledger
-> learning ledger
-> checkpoint
-> crash
-> resume
-> replay
-> audit

The implementation may use a small corpus, tokenizer and model. The goal is not scale. The goal is to prove that the data system is correct, reproducible, auditable and efficient.

The system must demonstrate:

Immutable tokenized shards with manifests
Frozen tokenizer and content hashes
Packing policies for different data types
Correct loss masks, attention masks and position ids
Curriculum stages, lane weights and protected floors
Evaluation and validation firewalls
OPUS acceptance, rejection, deferral and protected-floor override
Training consumption and learning ledgers
Token-level or sample-level loss tracking
Checkpoints tied to ledger offsets
Crash recovery without skipped or repeated batches
Replay of the same historical data stream
Forking from an earlier checkpoint
Packing utilization and useful loss-bearing tokens per second

The final run must deliberately crash, resume from the saved checkpoint and prove that the next batch is exactly the expected batch. It must also replay an earlier interval and prove that the reconstructed batch ids, token spans and hashes match the original run.
Submission

Submit a GitHub repository containing:

The complete implementation.
A short README explaining the architecture and design decisions.
One command that runs the complete demonstration.
Automated tests for the important invariants.
A generated execution log.
A machine-readable evidence bundle.
Generated manifests, ledgers, checkpoints and performance reports.

The complete system should run using one command, such as:

python run_demo.py

The exact command may differ, but it must execute the full demonstration without manual intervention.

The submission must generate the following structure:

submission_artifacts/
run.log
evidence.json
evidence.md
manifests/
ledgers/
checkpoints/
performance.json

Execution Log

run.log must contain the complete sequence of events:

shards created
manifests validated
evaluation data blocked
mixture compiled
batches packed
OPUS decisions recorded
checkpoint saved
crash simulated
run resumed
historical stream replayed
branch forked
audit completed
performance measured

Important events should be recorded clearly:

[PASS] tokenizer_hash_verified
[PASS] eval_shard_blocked
[PASS] checkpoint_saved
[PASS] resume_next_batch_matched
[PASS] replay_hash_matched

Evidence Bundle

evidence.json must record whether every major requirement passed and where the supporting evidence can be found.

evidence.md must provide a short human-readable summary:
Requirement Result  Evidence
Tokenizer integrity PASS/FAIL   Manifest record
Evaluation firewall PASS/FAIL   Blocked-shard event
Packing correctness PASS/FAIL   Packed-batch report
Mixture compliance  PASS/FAIL   Planned versus actual shares
OPUS audit trail    PASS/FAIL   Candidate decision records
Crash recovery  PASS/FAIL   Expected and resumed batch ids
Replay  PASS/FAIL   Original and replay hashes
Learning trace  PASS/FAIL   Loss linked to source data
Throughput  PASS/FAIL   Performance report

The evidence bundle must be generated by the implementation. Hardcoded evidence will not be accepted.
Evaluation

The assignment carries 1,000 points.
Area    Points
End-to-end execution    150
Shards, manifests and tokenizer integrity   100
Packing, masks and batch correctness    150
Mixture schedule, protected floors and OPUS 150
Consumption and learning ledgers    150
Checkpoint, crash, resume, replay and fork  150
Evaluation and validation firewall  50
Throughput and packing efficiency   50
Tests, evidence quality and documentation   50
Total   1,000

Evaluation will happen in three steps.
Step 1: Execute

The submitted command will be run to regenerate the complete submission_artifacts/ directory.
Step 2: Verify Evidence

The execution log, evidence.json and evidence.md will be checked against the generated manifests, ledgers and reports.
Step 3: Inspect Code

The code will be inspected to verify that the evidence was produced by the implementation and that the required behaviour was not simulated or hardcoded.

A subsystem receives full credit only when its result is supported by reproducible evidence.

Examples:

If resume repeats or skips a batch, the resume section fails.
If replay produces different batch hashes, the replay section fails.
If evaluation data enters a loss-bearing batch, the firewall section fails.
If reported packing or throughput numbers cannot be reconstructed, those claims will not receive credit.

The assignment is complete only when the system can prove what it consumed, why it consumed it, what the model learned from it and how the run can be reconstructed.
